The leaderboard is the only all-users data on the web and it is a 3-hop pipeline: Postgres mirror (schema sip_solana, written by the keeper) -> keeper recomputes an in-memory JSON snapshot every 120 s and right after each settlement write -> keeper serves GET /leaderboard (public, CORS *, max-age=30) -> the web reads that one URL server-side (env NAME SIP_SOLANA_KEEPER_URL, Next fetch revalidate 60 s, 6 s timeout), re-validates and REBUILDS the object, and renders /leaderboard (page) and /api/leaderboard (JSON proxy). No chain scan is involved and the website holds no DB connection. All amounts are lamports as decimal strings; no USD, USDC or bps in the payload; timestamps are ISO strings and YYYY-MM-DD UTC days. Global numbers already in the payload are only coverage.subjects, coverage.settlements, coverage.firstDay/lastDay and computedAt; saved/traded totals exist only as sums of per-vault entries (exact while <=100 vaults per board). There is no automatic sample fallback: keeper unset/down/503/bad shape gives an explicit "The rankings are unavailable" card; sample rows appear only with ?demo=1 and carry a badge. The keeper HTTP server serves GET/HEAD /health, /status, /leaderboard and (profit keeper, doorbell on) POST /hooks/helius, nothing else. In the DB or keeper memory but served nowhere: settlement mode and base_raw, investment_event (purchases), vault (owner, last charged rate), per-day rows (time series), on-chain vault state. Live, verified 2026-09-30 15:05Z: 1 vault with settlements, 9 settlements, 186381968 lamports saved, 18975900614 lamports traded, days 2026-09-19..2026-09-25, every season board empty; both keepers live and each discovers 2 links.

### Metrics

- **Vaults with at least one settlement ("pensions")** (exists-today). Source: GET /api/leaderboard -> coverage.subjects (keeper leaderboard.ts:353). Live 1. Counts vaults with any settlement row (incl. zero-contribution rows), within the 50,000 newest (vault,day) groups. NOT vaults that exist on chain, NOT users.
- **Total settlements** (exists-today). Source: GET /api/leaderboard -> coverage.settlements (leaderboard.ts:354, sum of count(*) per vault-day). Live 9. PROFIT and VOLUME mixed, no split.
- **First / last active day** (exists-today). Source: coverage.firstDay / coverage.lastDay (YYYY-MM-DD UTC, leaderboard.ts:355-356). Live 2026-09-19 .. 2026-09-25.
- **Data freshness** (exists-today). Source: computedAt (ISO) in the snapshot. Already rendered as 'Updated <timeAgo>' (leaderboard-view.tsx:215). Observed 5 min 23 s old through the Vercel proxy.
- **Total saved, all time (lamports -> SOL)** (derivable-cheap). Source: BigInt sum of boards.ahorro.all[].amountRaw (or boards.total.all[].amountRaw). Exact only while <=100 vaults per board (MAX_ENTRIES). In ?demo=1 only boards.total is filled. Proper fix: sum contributionRaw over rows in computeLeaderboard — then the web parser must be extended (it drops unknown fields). Live sum 186381968 lamports.
- **Total volume traded, all time (lamports)** (derivable-cheap). Source: BigInt sum of boards.total.all[].volumeRaw. Same <=100 cap. volumeRaw optional on the web type. 0 for backfilled/pre-column rows (live: 8 of 9 settlements carry volume); profit keeper writes tradedLamports, volume keeper writes volumeLamports (keeper.mts:1539) — two measures in one column; measured, never attested. Live sum 18975900614.
- **Saved / traded / settlements / active vaults THIS WEEK** (derivable-cheap). Source: boards.total.season[] (sum amountRaw, volumeRaw, settles; length = active vaults). Week = Monday 00:00 UTC. Live: every season board is empty -> zeros. Same <=100 cap.
- **Average saved per vault, settles per vault, total active days, longest streak** (derivable-cheap). Source: boards.total.all[] entries (amountRaw, settles, activeDays, bestStreak). Same top-100 caveat; with 1 vault live these are that vault's numbers.
- **Daily time series (saved/day, volume/day, settlements/day, active vaults/day)** (derivable-cheap). Source: DayTotals rows returned by SolanaReadModel.leaderboardDays() (read-model.ts:363-385), in keeper memory at each refresh (keeper.mts:799), not served. Needs a new field in the snapshot or a new keeper route, plus web parser support, plus a keeper redeploy. This is what any chart needs. Live it would be 3 active days.
- **Settlement split by mode (PROFIT vs VOLUME): count and contribution** (derivable-cheap). Source: sip_solana.settlement_event.mode (sql:35), not selected by the leaderboard query. One extra GROUP BY in the keeper (pool max 2, 5 s timeout, must stay off the sweep path). Live value not checked (no DB access).
- **Total measured base (profit measured / notional charged on)** (derivable-cheap). Source: sum(settlement_event.base_raw) grouped by mode (sql:36). Meaning depends on mode: profit lamports (0) vs notional lamports (1); never add across modes.
- **Trading wallets linked / distinct vaults linked (incl. never settled)** (exists-today). Source: keeper /status linksDiscovered (keeper.mts:1124); distinct vaults from the sweep's doorLinks (keeper.mts:1139-1145). linksDiscovered is served today (live 2) but the web reads /status nowhere, /status has no CORS header and the app CSP blocks the keeper origin -> needs a server-side read or a small aggregate added to the snapshot. Distinct-vault count is in memory only.
- **Current vault mode split, paused count, rates** (derivable-expensive). Source: VaultState.skimMode/skimBps/volumeBps/paused (accounts.ts:74-91) from the sweep's batched read (keeper.mts:1178). Downgraded: that read covers only the links the sweep TURNS; on the profit keeper (doorbell on) that is a selection. A complete split needs a dedicated read of every linked vault. /status exposes mode only as free text in wallets[].detail on the volume keeper.
- **Total invested (USDC) / number of purchases / purchases per target mint** (derivable-cheap). Source: sip_solana.investment_event: spent_raw, received_raw, target, at (sql:44-53), written at keeper.mts:1622. No reader exists. spent_raw is USDC raw units (invest-tick.ts:117, 1093, 1108) and can be summed; received_raw is per-target-mint raw units and cannot be summed across targets. Only the profit keeper writes it.
- **Unique owners** (derivable-cheap). Source: count(distinct owner_addr) from sip_solana.vault (sql:16-21). Table only has vaults that settled at least once (recordLink is inside the SETTLED branch).
- **Saved total in USD at today's SOL price** (derivable-cheap). Source: lamports total x SOL/USD from loadPrices().sol.oracle.microUsd or .pool.microUsd (web prices-data.ts:537-543, 663). Server-side only, two batched RPC calls, a Reading that can fail. Today's price, not the price at settlement time — must be labelled so (the pension page already uses 'at today's SOL price', pension-stats.tsx:48).
- **TVL (current vault balances) and USD at settlement time** (derivable-expensive). Source: not in this pipeline: no vault balance and no price is stored in the mirror. Would need per-vault SOL + token account reads and prices; nothing in read-model.ts or leaderboard.ts does it.
- **Keeper liveness (both keepers): mode, lastSweepAt, sweeps, sweepMsP50/P90, skipped, crank balance, history** (exists-today). Source: GET <keeper>/status fields of the same names (status.ts:182-282). Two services, two hosts (README.md:77-78); the web knows one keeper URL. sweeps/skipped/failovers reset on restart. Operator data, not curated for a public page.
- **Losses pending carry** (exists-today). Source: /status pendingCarries[].lossLamports (status.ts:108-122). In memory only, dropped on restart. Live: empty on both keepers.
- **Total number of vaults on chain (incl. unlinked)** (derivable-expensive). Source: would need getProgramAccounts on Vault accounts; the keeper scans only TradingLink (discovery.ts:50-53). Cheap approximation: distinct vaults among discovered links.

### Traps

- No automatic sample fallback. Keeper down/unset -> explicit Unavailable card (leaderboard-view.tsx:203, 165-182); sample only via ?demo=1 (page.tsx:45) with badge 'Sample data — not real pensions' (leaderboard-view.tsx:225-227). A dashboard must keep 'unavailable' distinct from 'zero' and label any sample the same way.
- SAMPLE_LEADERBOARD fills only boards.total; ahorro/volumen are [] (leaderboard-sample.ts:124-125). Totals summed from boards.ahorro in demo mode come out 0.
- Summing per-vault entries undercounts past 100 vaults: MAX_ENTRIES=100 per board (keeper leaderboard.ts:47, 305). coverage.* is not sliced but is bounded by LEADERBOARD_DAY_LIMIT=50,000 newest (vault,day) groups (read-model.ts:79). Real global totals should be summed in the keeper from rows.
- Adding fields to the keeper snapshot is not enough: parseLeaderboard rebuilds the object and drops unknown fields (web lib/leaderboard.ts:211-223) and /api/leaderboard returns the parsed object (route.ts:31). It also returns null — whole board 'unavailable' — if unit/rules/boards/coverage stop matching (lib/leaderboard.ts:185-186, 192, 197, 203). Keep changes additive.
- Keeper (Railway) and web (Vercel) deploy separately: the web type already treats volumeRaw/breakdown/pointsExact as optional for an older keeper (lib/leaderboard.ts:40-54). Any new global field must be optional on the web or the page breaks until the keeper is redeployed.
- A browser cannot fetch the keeper from this app: CSP connect-src is a fixed list without the keeper origin (security-headers.mjs:148-162) and the policy is pinned by scripts/check-csp.mts (prices-data.ts:5-11). The keeper's CORS * (status.ts:634) only helps other origins. Read server-side like page.tsx:50, or through a same-origin /api route.
- coverage.subjects is 'vaults with a settlement row', not users: live it is 1 while both keepers discover 2 links. One person can hold several vaults; subject is the VAULT address (keeper leaderboard.ts:23-27, 91).
- coverage.settlements counts every row; entry.settles on 'ahorro' excludes zero-contribution days and on 'volumen' excludes zero-volume days (leaderboard.ts:131-135). Live proof: ahorro settles 9 / 3 days, volumen settles 8 / 2 days for the same vault.
- All money is lamports as DECIMAL STRINGS; use BigInt + formatSol (truncates, 4 dp; lib/leaderboard.ts:268-279). Number() would round. No USD/USDC/bps in the payload; rules.sizeUnit is lamports.
- volumeRaw is not a money-grade number: measured never attested (sql:67-71), 0 for backfilled rows and rows written before the column existed (backfill-settlements.mts:21-25), and the two keepers write different measures into it (keeper.mts:1537-1539).
- Staleness stacks: keeper recompute 120 s (+ on each settle) -> keeper max-age=30 -> Next fetch revalidate 60 -> route s-maxage=60 + stale-while-revalidate=300. Observed live: x-vercel-cache STALE, age 299, payload computedAt 5 min 23 s old while the keeper's own copy was 4 min newer. computedAt is the only honest freshness indicator.
- The leaderboard view opens on 'This week' (useState 'season', leaderboard-view.tsx:201) and every season board is empty live (last activity 2026-09-25, season began 2026-09-28). A 'this week' tile on real data shows zeros today — design the empty state; the existing copy for it is at leaderboard-view.tsx:249-253.
- Real data is tiny: 1 vault, 9 settlements, 3 active days. A time-series chart or a top-N list on live data will look empty; decide what the page shows at N=1 before designing for N=1000.
- Two keepers (profit, volume) each compute and serve /leaderboard from their own DATABASE_URL (config.ts:761, 801). The web reads exactly one; the runbook names the profit keeper (docs/runbooks/VERCEL_WEB.md:55). Live both serve identical coverage and rows, consistent with one shared database — not proven from code.
- /status is public and unauthenticated (status.ts:241-243) but carries operator detail (privy ids, wallet addresses, webhook sync errors, free-text details). No CORS header. Do not proxy it whole to a public page — project a small aggregate.
- Redaction tripwire can replace /leaderboard or /status with {service,status:'withheld: redaction tripwire'} at HTTP 200 (status.ts:387-393, 413-419); the web then reports 'not a leaderboard this build understands' (lib/leaderboard.ts:253).
- Keeper DB budget is tight by design: pool max 2, 5 s statement/query timeout (read-model.ts:128-139), and DB work must never sit on the sweep path (keeper.mts:745-756). Any new aggregate belongs on refreshLeaderboard's cadence, must tolerate null, must keep the last good payload, and must not throw (runs under an uncaughtException trap that exits, keeper.mts:806-808).
- Adding a keeper route is not free: the 404 body hard-codes the path list twice (status.ts:588, 651) and tests pin it and the 'nothing else' surface (test/status.test.ts:295, 402).
- The mirror tables are not a registry: vault/trading_link rows are written only on a SETTLED (keeper.mts:1521-1523), trading_link.active is never set false (read-model.ts:343-347), vault.skim_bps is the last charged rate of whichever mode (read-model.ts:327-334). Do not present count(vault) as 'vaults created'.
- The keeper's per-sweep vault read is not a full census: it reads only the vaults of links that sweep turns (keeper.mts:1177-1178). A 'vaults by mode' tile built on it would undercount on the profit keeper whenever the doorbell is trusted.
- investment_event: spent_raw is USDC raw (6-decimals mint, invest-tick.ts:117) and summable; received_raw is per-target-mint raw units and is meaningless summed across targets. `at` is the writer's clock (no block time passed, keeper.mts:1622-1629). Nothing reads this table today.
- settlement_event.at falls back to now() when the receipt gave no blockTime (read-model.ts:285; keeper.mts:1546); day bucketing is UTC (read-model.ts:370) — a local-time chart axis shifts days.
- /status counters (sweeps, skipped, failovers, doorbell events) reset on every keeper restart/deploy; they are not lifetime totals. Live numbers in this map move every minute.
- A sibling stats page should follow /leaderboard: force-dynamic, `now` resolved once on the server and passed down to avoid hydration mismatch, no Privy provider for strangers (page.tsx:8-12, 36, 51-73). The fully server-rendered precedent with no client component is /prices/view (prices/view/page.tsx:9-13).
- Adding a tab touches more than one file: SiteHeader `current` union (site-header.tsx:52) and nav array (72-79); the header nav is hidden below md (site-header.tsx:126), so the footer LINKS list (site-footer.tsx:38-45) is the mobile door; tests pin mode-carrying links for '/activity' and '/leaderboard' (dashboard-shell.test.ts:203; site-header.test.ts:36, 57). The new page must carry ?mode= like page.tsx:48-49 does.
- Keeper image: cross-package files are COPYed by name (Dockerfile:66-107; test/dockerfile-copies.test.ts), so a new keeper import from another package can be green locally and break the image; and the repo-root Dockerfile must stay byte-identical to the keeper's (Dockerfile:12-20; test/dockerfile-copy.test.ts). Files inside packages/solana-keeper are copied whole (Dockerfile:109).
- Owner decision on the leaderboard: no scoring formula or thresholds printed on the page (leaderboard-view.tsx:256-261; page.tsx:96-101). A stats dashboard should not surface rules.* as headline content.
- USD on the web means 'at today's SOL price' read server-side from Pyth/pool (prices-data.ts:537-543, 663), a Reading that can fail and is never cached (prices/route.ts:21-24). There is no historical price anywhere, so a USD time series cannot be honest.
- Session memory, not re-verified in code: work lands on branch post-submit, never main, until 2 Oct; DB/env/program are not isolated by branch, so a keeper change only takes effect when the Railway service is redeployed and both branches share the live database; public brand is SaverFi (no 'SIP'/'Nuvem' in visible copy); Next dev must be opened on localhost, not 127.0.0.1; keeper tests need Node 22.

## 2. The program, the keeper and the Postgres mirror

CORRECTIONS: 11 — (1) "invest/convert/withdraw/... leave no log line" was wrong: no emit!/msg! exists, but Cargo default features do not enable no-log-ix-name, so Anchor's "Program log: Instruction: <Name>" line is emitted for every instruction (names yes, amounts no); (2) keeper HTTP surface re-cited to status.ts:547 and POST /hooks/helius exists only when the doorbell is on; (3) trade COUNTS are measured in memory by both keepers (WindowMeasurement.txCount / successfulTradeCount / walletSignedTxCount) — only never carried out of the turn or persisted; (4) the TradingLink list is a sweep-local variable, only its length is retained, so "sum of nonces already in keeper memory" needs stashing; (5) "lifetime_invested is USDC" is conditional: in_mint is rewritable by set_invest_policy while counters survive, and the owner may crank invest himself; (6) leaderboard `coverage` is global only under the 50,000 (vault,day)-group cap and counts zero settles; (7) settlement `at` fallback is the DATABASE's now(), not the keeper's clock; (8) "no sqlite/Supabase anywhere" narrowed to what package.json shows; (9) linksDiscovered is exists-today only on the keeper's /status — the web proxies /leaderboard only; (10) line fixes (rules.ts:37, addresses.ts:157, product.ts:691, state.rs:251 + invest.rs:137); (11) the "Vault offsets not read" open question replaced by derived offsets plus a new trap that InvestmentPolicy has NO fixed offsets after its legs vec. State today: the on-chain program sip_vault (6kA9H9zQ…) has 4 account types and exactly one event, Settled (slots, no timestamp). Cumulative counters on chain: Vault.lifetime_saved (lamports, written only in settle, never decremented) + Vault.created_at + current mode/rates; TradingLink.settlement_nonce (restarts on relink, account closed on unlink); InvestmentPolicy.lifetime_invested + 31 day-buckets (in_mint raw, whole basket, no per-asset split). ### Traps

- NEVER add base across modes. PROFIT base_lamports = net cash profit of the window (cashDelta - deposits + withdrawals, net of carried losses; measure-window.ts:566, settle-decision.ts:641), charged at 201..10000 bps. VOLUME base_lamports = notional of every buy AND sell after the last mode/rate change (volume-base.ts:48), charged at 1..200 bps. Same column (settlement_event.base_raw / Settled.base_lamports), told apart only by `mode`. The only cross-mode-addable money figure is paid (contribution_raw / lifetime_saved).
- settlement_event.volume_raw is a third quantity and is itself mixed (keeper.mts:1539): profit-keeper rows hold tradedLamports (any successful non-flow tx's SOL delta, token-account rent included), volume-keeper rows hold volumeLamports (probe rule, ALL counted trades in the window before the policy boundary, so it can exceed base_raw on the same row). Backfilled rows and rows older than the column are 0.
- One event only (Settled), with slots and no timestamp. Invest, convert, wrap, withdraw, link, unlink and policy changes emit no event; logs carry only Anchor's 'Instruction: <Name>' line, no amounts. Amounts need instruction decoding + pre/post balances per transaction (packages/solana-core/src/client/activity.ts shows how, per vault).
- Vault.lifetime_saved is gross lifetime inflow from settles only (settle.rs:171): it ignores withdrawals and plain SOL deposits and says nothing about the current balance. Do not label it TVL or balance.
- Vault.skim_mode / skim_bps / volume_bps are the CURRENT policy (set_policy.rs:33). For 'saved by mode' use the per-settlement mode (settlement_event.mode / event), never the vault's current mode.
- Nothing global is in keeper memory: the TradingLink list is a local of each sweep (keeper.mts:1110), vault policy fields are read only for turned links, lifetimeSaved/createdAt/lifetimeInvested are not decoded (accounts.ts:74, 223). Vaults with no linked wallet are unknown to the keeper. A stats figure needs a NEW getProgramAccounts (dataSize 125 and 970) or SQL.
- InvestmentPolicy has NO fixed byte offsets after `legs` (borsh Vec is variable length inside a fixed 970-byte allocation; fieldOffset throws, borsh.ts:365). No memcmp/dataSlice on buckets or lifetime_invested: fetch whole accounts and decode with decodeInvestmentPolicy. At ~1.3 KB base64 per policy the web pool's 8 MiB response cap (solana-core/src/server/rpc-pool.ts:32) is reached at a few thousand policies.
- lifetime_invested and the buckets are in in_mint raw units and survive a set_invest_policy that changes in_mint (set_invest_policy.rs:73,79); the owner can also crank invest himself (invest.rs:113). Treat as USDC only after checking policy.inMint == USDC_MINT, and know a changed in_mint leaves mixed units.
- The mirror is best-effort: writes are fire-and-forget (read-model.ts:398), no row without DATABASE_URL, no row when the settle's signature was never learned (Privy 504, keeper.mts:1495; nonce-moved path, settle-tick.ts:501), and investment rows have no backfill. DB totals can be lower than chain totals: headline totals from chain counters, time series from DB, and do not expect exact reconciliation.
- settlement_event PRIMARY KEY is (wallet_addr, nonce) but the chain nonce restarts at 0 on relink (link_wallet.rs:117). The upsert (read-model.ts:286-291) then overwrites contribution_raw/volume_raw/tx_ref/height of the OLD row while keeping its old vault_addr, mode, base_raw and at. (wallet, link_epoch, nonce) is the real unique key (events.rs:19-24); link_epoch is not stored. A backfill run has the same effect.
- The keeper's pg pool is max 2 with 5 s statement/query/connection timeouts, and an armed keeper pins one connection for its advisory lock (read-model.ts:128-139, 169). A new stats query on that pool competes with recordSettlement for the single free connection; a write that cannot get a connection in 5 s is dropped for good. Keep any aggregate well under 5 s, on a timer like the leaderboard (keeper.mts:757), never per request; or give stats its own pool.
- sip_solana.vault.created_at and trading_link.linked_at are mirror insert times (sql:20,26), vault.skim_bps is the rate of the last settlement (volume rate for VOLUME vaults, read-model.ts:327-333), trading_link.active is never set false (read-model.ts:346). Use chain accounts for vault count, creation dates, mode and link state.
- investment_event.at is the DB clock, height is a getSlot read after the purchase (not the tx slot), spent_raw is the leg's budget share, not the measured spend (invest-tick.ts:1106-1111). received_raw is in each target mint's own raw units; SPYx display amounts are scaled and must not be computed as raw / 10^decimals (activity.ts:18-20).
- settlement_event.height is the session END slot of the settled window (keeper.mts:1541), not the settle transaction's slot; `at` is the receipt blockTime when read, otherwise the DATABASE's now() (read-model.ts:285).
- Zero-base settlements are real rows and events (settle.rs:138). 'Settlements per day', 'active savers' and the existing coverage numbers include them unless filtered on contribution_raw > 0; the savings board excludes them (leaderboard.ts:131-135).
- leaderboardDays() is capped at the 50,000 newest (vault, day) groups (read-model.ts:79) and /leaderboard returns at most 100 entries per board (leaderboard.ts:47): global sums cannot be rebuilt from the payload, and `coverage` itself is computed from the capped rows. Write a dedicated aggregate. If the /leaderboard payload is extended, the web parser reads known keys only (website lib/leaderboard.ts:181), so new fields are ignored until it is taught them.
- TradingLink-derived counts undercount history: unlink CLOSES the account (unlink_wallet.rs:46); summing nonces gives 'settlements by currently linked wallets since their last link'.
- A program-id history scan reads EVERY sip-vault transaction by anyone, one getTransaction each; the existing backfill defaults to 5 pages x 1000 signatures at 120 ms on a single endpoint and must pass maxSupportedTransactionVersion 1 (measure-window.ts:176). Do not run such a scan inside the keeper process: its pool has no rate limiter and one 429 sets that endpoint aside for 30 s for the money path too (rpc-pool.ts:25, 85-89). History older than the RPC's retention ('~2-3 days' per read-model.ts:9) is not recoverable from a normal endpoint.
- Invest buckets are per vault, indexed day % 31 with stale entries left in place (state.rs:251): filter with bucket_days[i] + 31 > today or old days (and the all-zero initial day 0) are summed into the chart. Total per day, no per-asset split.
- getProgramAccounts cannot be issued from the browser (relay-policy.ts:317). The keeper's /status and /leaderboard are public and unauthenticated. A stats route must be server-side and cached, with request cost independent of the caller (precedent: compute on a timer in the keeper, 30 s cache header, web revalidate 60 s).
- Two keeper services exist (profit, volume; SIP_SOLANA_ROLE, config.ts:801), each with its own /status, in-memory state and own /leaderboard payload. The web is pointed at ONE keeper URL (SIP_SOLANA_KEEPER_URL). A /stats added to the keeper is served by whichever service that URL names; per-keeper memory figures cover only that role.
- Units must be labelled per figure: lamports (1e9/SOL) for base, owed, paid, lifetime_saved, volume_raw; USDC raw (1e6) for lifetime_invested, buckets, spent_raw; bps for rates; SLOTS (not time) for epoch, frontier, height, session windows; unix seconds for created_at. Amounts exceed a JS double: keep them as strings/BigInt end to end (the leaderboard payload uses decimal strings, leaderboard.ts:106-110).
- DATABASE_URL for the keeper must be a session connection; port 6543 (transaction pooler) is refused at boot (config.ts:767-775). The web has no pg dependency today and the SQL file says the web only reads via the keeper; adding a direct DB reader to the web is a new dependency and a new secret on Vercel, not an existing path.

### Traps

- CSP is pinned by a golden string checked in prebuild and verify (scripts/check-csp.mts:28-36, 142; package.json:11, 20). A client fetch to the keeper/Helius/any third party, an <img> from a new host, a web font or a chart script from a CDN is blocked in the browser with no server trace; script-src additionally fails the check on any origin beyond self/inline/Turnstile (check-csp.mts:134-136). Fetch everything server-side and pass props or serve it from a same-origin route; recharts is bundled so it is fine.
- Copying the /prices pattern for an RPC-heavy read is dangerous: loadPrices is force-dynamic, no-store, builds a fresh RpcPool per request and charges NO limiter (prices-data.ts:677). A stats route doing getProgramAccounts that way is one program scan per visitor/bot on the web's Helius key, which code comments say the keeper shares (readers.ts:1189, solana-core config.ts:80-81).
- A program scan that times out or is throttled BENCHES that endpoint for 30 s in its pool (rpc-pool.ts:29, 247-259; fault list 90-103). With several endpoints the pool just fails over, and with all benched it tries all anyway (185-192), so it is not an outage by itself — but each attempt can take 20 s (line 30), i.e. up to 20 s x endpoints before 'unreadable', and the metered read routes only allow maxDuration 60. A new route needs its own maxDuration and a call timeout.
- An unfiltered getProgramAccounts answer is capped at 8 MiB (rpc-pool.ts:32); past it ResponseTooLargeError is THROWN with no failover (220-224). Far away at 125-byte vaults, closer for 970-byte InvestmentPolicy accounts; it is a hard ceiling, not a degradation.
- Rate-limit buckets and the shared reads budget are in memory per Vercel instance (rate-limit.ts:3-6): not a global guarantee. The only protection that holds across instances is a shared HTTP/data cache, as /api/leaderboard (s-maxage) and fetchLeaderboard (next.revalidate) use.
- Never cache a failure and never return an empty/zero payload at 200 in place of a failure: 503 + no-store on failure, s-maxage only on success (api/leaderboard/route.ts:24-35); 'unreadable' vs 'missing' is a product rule (readers.ts:1-6). Note the one existing violation-shaped spot: parseLeaderboard turns a missing coverage number into 0 (leaderboard.ts:217-218) — a stats tile reading coverage must treat 0 with care or tighten the parser.
- The keeper's boards are truncated to 100 rows (solana-keeper/src/leaderboard.ts:47, 305): summing amountRaw/volumeRaw over any board under-counts once more than 100 vaults qualify. coverage.subjects/settlements are not truncated by that, but they ARE bounded by the 50,000 (vault,day)-group SQL limit, newest first (read-model.ts:79, 376-377), so firstDay and the totals silently stop growing backwards past it.
- coverage comes from the keeper's Postgres mirror, not the chain: it counts vaults with at least one recorded settlement row (including zero-contribution settles, leaderboard.ts:353), not vaults that exist; mirror writes are fire-and-forget and only on SETTLED (keeper.mts:1500-1553), and volume_raw is 0 for rows written before the column existed (sql/sip_solana.sql:67-73). 'Users' from coverage.subjects != Vault accounts on chain != on-chain sum of lifetimeSaved.
- The web knows ONE keeper URL while there are two keeper services. By code and runbook both share one database (singleton.ts:24-27; RAILWAY_SOLANA.md:529-530) and the board query has no mode filter (read-model.ts:369-377), so the profit keeper's /leaderboard includes volume settlements — but each keeper recomputes on its own 120 s timer or after ITS OWN settle (keeper.mts:757, 1553), so a volume settle can take up to ~2 min to appear on the profit keeper's board, plus 60 s of web cache. Whether production is actually deployed as the runbook says was not verifiable from the repo.
- /status of the keeper is public but operator-oriented: it lists every trading wallet with its last outcome and detail text (status.ts:275), signer ids and crank balance. Proxy only whitelisted numeric fields (linksDiscovered, lastSweepAt, sweeps, mode, config.paused) through a parser like parseLeaderboard; never pass the payload through. It has no CORS header (status.ts:625-627), so it must be read server-side anyway.
- Adding a keeper endpoint is a keeper deploy with its own traps: httpHandler's 4 required args and the 404 path list are pinned by test (status.ts:547-563, 651; test/status.test.ts:402); the query must run on its own cadence, never inside the sweep or per request (keeper.mts:746-756); the pool has 2 connections and a 5 s statement timeout shared with settlement history writes (read-model.ts:128-140); imports from other packages need a named COPY in the Dockerfile (Dockerfile:66-68, 101-107).
- Vercel Preview carries SIP_SOLANA_KEEPER_URL but not the Helius key (docs/runbooks/VERCEL_WEB.md:49, 55, 75-76) and sits behind Vercel login (36): a stats page built on the web's RPC renders degraded/503 on every preview, one built on the keeper proxy works there — against PRODUCTION keeper data.
- `next: { revalidate }` is honoured under force-dynamic only because it is explicit (patch-fetch.js:366-373). Adding `cache: 'no-store'` or dropping the revalidate makes every page view hit the keeper; a fetch carrying an authorization/cookie header can be auto-uncached in a dynamic context (patch-fetch.js:380, 400). Verified in Next's source only, not measured in production.
